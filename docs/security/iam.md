# IAM and Authentication Design

This document describes every permission CloudSentry holds, on both sides of the cross-account boundary,
and where caller identity is verified. The implementation lives in `infrastructure/` (platform side) and
`packages/shared-types/src/permissions.ts` (customer side).

## 1. Principles

1. **Read-only in customer accounts.** The customer role grants only `Describe*`, `Get*` and `List*` actions.
   CloudSentry cannot stop, delete, or modify customer resources in the MVP.
2. **No long-lived customer credentials.** CloudSentry never asks for access keys. It assumes a customer-deployed
   role with STS; temporary credentials exist only in Lambda memory for one invocation and are never written to
   DynamoDB, S3, logs, or Step Functions state.
3. **One permission set per function.** Each Lambda has its own execution role containing only what its code path needs.
4. **Tenant identity is resolved server-side** from the verified token subject, never from request input.

## 2. Customer-side role

Customers deploy a role named `CloudSentry*` (default `CloudSentryReadOnlyRole`) from the onboarding template
generated by the API (the same template can be printed with
`cd infrastructure && npx tsx scripts/print-customer-template.ts`).

Trust policy:

```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::<PLATFORM_ACCOUNT_ID>:root" },
  "Action": "sts:AssumeRole",
  "Condition": { "StringEquals": { "sts:ExternalId": "<external id generated by CloudSentry>" } }
}
```

Permissions (`CUSTOMER_ROLE_PERMISSION_STATEMENTS`):

| Purpose            | Actions                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Discovery          | `ec2:DescribeRegions`, `ec2:DescribeInstances`, `ec2:DescribeVolumes`, `ec2:DescribeAddresses`, `ec2:DescribeSnapshots`, `ec2:DescribeNatGateways`, `rds:DescribeDBInstances`, `elasticloadbalancing:DescribeLoadBalancers`                                                                                                                                                                                                                                                                                                                                                                                                           |
| Extended discovery | `lambda:ListFunctions`, `lambda:ListProvisionedConcurrencyConfigs`, `eks:ListClusters`, `eks:DescribeCluster`, `eks:ListNodegroups`, `eks:DescribeNodegroup`, `eks:ListFargateProfiles`, `elasticache:DescribeCacheClusters`, `cloudfront:ListDistributions`, `elasticfilesystem:DescribeFileSystems`, `elasticfilesystem:DescribeLifecycleConfiguration`, `dynamodb:ListTables`, `dynamodb:DescribeTable`, `application-autoscaling:DescribeScalableTargets`, `redshift:DescribeClusters`, `backup:ListBackupPlans`, `backup:GetBackupPlan`, `backup:ListBackupVaults`, `backup:ListRecoveryPointsByBackupVault`, `tag:GetResources` |
| Utilization        | `cloudwatch:GetMetricData`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Cost               | `ce:GetCostAndUsage`, `ce:GetCostAndUsageWithResources`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Metadata           | `iam:ListAccountAliases`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

These actions do not support resource-level restrictions, so `Resource: "*"` is required; none of them can change state.

None of the extended-discovery actions read data contents: they return configuration and metadata only
(no DynamoDB items, no Lambda code or environment variables are requested — `ListFunctions` does return function
configuration including environment variable _names and values_ if present, so CloudSentry discards the
`Environment` field during mapping and never stores or logs it). Recovery-point listing returns sizes, dates and
resource ARNs, not backup contents.

Roles created from templates generated before the extended services were added lack these permissions. Scans then
report those resource types as failed (AccessDenied per region) and complete as PARTIALLY_COMPLETED; verification
lists them as DENIED and the dashboard asks the customer to update the CloudFormation stack.

### External ID and the confused-deputy problem

Trusting the CloudSentry account alone would let any CloudSentry tenant who learned another customer's role ARN
ask CloudSentry to scan that account. The external ID closes this gap:

- CloudSentry generates the external ID (`cs-` + 192 random bits). Clients can never choose or change it.
- Each registered account stores its own external ID; the scanner always passes the external ID of the account
  record it loaded from the caller's tenant partition.
- AssumeRole succeeds only if the customer's trust policy contains that exact value, i.e. only for the tenant that
  generated it.

Account ID verification: after AssumeRole, CloudSentry calls `sts:GetCallerIdentity` with the temporary credentials
and rejects the connection if the account differs from the registered account ID. The role ARN's account must
also match the registered account ID at input validation time.

## 3. Platform-side IAM (per function)

All DynamoDB grants are key-based only (`GetItem`, `BatchGetItem`, `Query`, `ConditionCheckItem`, plus
`PutItem`, `UpdateItem`, `DeleteItem`, `BatchWriteItem` for writers). `Scan` and table-management actions are never
granted. S3 grants are limited to the `scans/` and `reports/` prefixes of the artifacts bucket; readers also get `s3:ListBucket`
so missing keys return 404 instead of 403. Every function additionally has CloudWatch Logs (its own log group) and
X-Ray write permissions.

`sts:AssumeRole` is only ever granted on `arn:aws:iam::*:role/CloudSentry*`. Because the API rejects role names
that do not start with `CloudSentry`, the platform cannot be used to assume arbitrary roles in other accounts.

### Service roles

- **EventBridge Scheduler execution role** (`cloudsentry-<stage>-scheduler`): can only `lambda:InvokeFunction` the
  scheduled-scan trigger. Its trust policy requires `aws:SourceAccount` = the platform account and
  `aws:SourceArn` = the CloudSentry schedule group, so other accounts' or groups' schedules cannot use it.
- **Step Functions role**: generated by CDK with `lambda:InvokeFunction` on exactly the workflow functions, plus
  log delivery and X-Ray.

### Tenant isolation limits

IAM does not isolate tenants from each other inside the platform: a function that can read the table can read
any partition. Isolation is enforced in code (repositories build every key from the caller's tenant, and
pagination cursors are validated against the tenant prefix) and verified by tests. A future hardening step is
STS session policies with `dynamodb:LeadingKeys` and S3 prefix conditions per tenant.

## 4. Authentication and token verification

Users authenticate against a Cognito user pool through the CloudSentry API (backend-mediated login):

1. `POST /api/v1/auth/login` -> api-auth calls Cognito `InitiateAuth` (`USER_PASSWORD_AUTH`) with the confidential
   client's `SECRET_HASH`. The client secret is read from Secrets Manager; only api-auth can read it.
2. The access token is returned in the response body (kept in memory by the dashboard). The refresh token is set as an
   `HttpOnly; Secure; SameSite=Strict` cookie scoped to `/api/v1/auth`. It is never readable by JavaScript.
3. `POST /auth/refresh` additionally requires the `X-CloudSentry-Client: web` header as a CSRF guard.
4. Logout revokes the refresh token (Cognito token revocation is enabled on the client).

The dashboard and API share one CloudFront origin (`/api/*` -> HTTP API), so the cookie is first-party and no CORS
policy is needed. CloudFront forwards `Authorization` and cookies to the API because the `/api/*` behavior uses the
`CachingDisabled` cache policy with the `AllViewerExceptHostHeader` origin request policy.

### Where tokens are verified, and why twice

**At the gateway.** Every route except `/api/v1/auth/*` uses an HTTP API JWT authorizer
(`HttpUserPoolAuthorizer`) configured with the user pool issuer and the app client ID as audience. Cognito access
tokens have no `aud` claim; HTTP API JWT authorizers validate `client_id` when `aud` is absent, so access tokens issued
to the CloudSentry client are accepted and tokens for any other client are rejected. The gateway also checks signature
(JWKS), `iss`, `exp`, `nbf` and `iat`. Unauthenticated requests are rejected before any Lambda runs, which bounds cost
and attack surface.

**In the Lambda.** The gateway cannot distinguish access tokens from ID tokens (both carry the client ID), and local
development has no gateway. Each API Lambda therefore verifies the bearer token again with `aws-jwt-verify`
(`tokenUse: "access"`, `clientId`), then loads `USER#<sub>` from DynamoDB to resolve the tenant and role. Claims
are never trusted for tenant or role. `/api/v1/auth/me` has no gateway authorizer (the `/auth/*` routes must be public
for login/refresh) and relies on the in-Lambda check.

Neither layer checks revocation for access tokens (JWT verification is offline). Access tokens live for one hour;
revoking the refresh token at logout prevents new access tokens.

### Authorization

Roles are stored on the user profile: `VIEWER` (read-only), `MEMBER` (scans, finding/recommendation status, reports),
`ADMIN`/`OWNER` (accounts, schedules, settings). Checks happen in the API handlers after tenant resolution.

## 5. Data protection

| Store                 | Protection                                                                                                                                                                         |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DynamoDB              | AWS-managed KMS encryption; PITR in staging/prod; deletion protection in prod                                                                                                      |
| Artifacts bucket      | Block Public Access, SSE-S3, TLS-only bucket policy (TLS 1.2+), bucket-owner-enforced ownership, lifecycle expiry: `scans/` (artifact retention) and `reports/` (report retention) |
| Dashboard bucket      | Private; readable only by the CloudFront distribution through Origin Access Control                                                                                                |
| Notifications topic   | Encrypted with the AWS-managed SNS key; TLS-only topic policy                                                                                                                      |
| Ops alarm topic       | TLS-only; not KMS-encrypted because CloudWatch alarms cannot publish to topics using the AWS-managed SNS key (contents are alarm metadata only)                                    |
| Cognito client secret | Secrets Manager; resolved at deploy time from the user pool client, never present in templates                                                                                     |
| Logs                  | Structured JSON with key-based redaction of credentials, tokens, cookies and external IDs; Step Functions logs exclude execution data                                              |

The dashboard is served with HSTS, `X-Frame-Options: DENY`, `nosniff`, a strict referrer policy and a CSP that
allows only same-origin resources. `script-src` includes `'unsafe-inline'` because a Next.js static export embeds inline
bootstrap scripts and a static site cannot issue nonces.
